## Shared compilation cache

Proposed next-plan choice, not implemented or dispatched: add an optional compilation-layer backend cache-policy seam and let PS3 opt out of both cache lookup and storage until dependency/toolchain identity can be represented end-to-end. Leave existing backends' default behavior unchanged. Service-level tests must use a cache that already contains a same-request stale result and prove PS3 still invokes the backend; mutate an included file, optimization/warnings/debug options, and configured toolchain between calls. Verify existing backends still hit/store normally. This avoids presenting a backend-local key as protection against a service-level cache hit. Cost: PS3 recompiles rather than reuses results; later caching needs explicit immutable dependency snapshots and format-version identity. Do not make a global cache redesign part of the current compiler task.

Additional direct contract check during Task4 implementation: ShaderBinding represents logical set/slot and constant-buffer size; ShaderConstantMember carries name/type/offset/size only, without matrix or array stride. ShaderVertexElement carries semantic/index/format only, not final RSX channel. Do not overload these generic fields with fragment relocation addresses or inter-stage routing indices. Keep full PS3 metadata in a platform-owned versioned payload, with a documented distinction between logical resource identity and hardware bindings. Ps3ShaderUniformMember currently provides leaf offsets/sizes, not the compiler-declared total constant-buffer size. The backend plan must obtain that size from reflection if the shared program definition requires it, rather than claim the maximum active member end is the declared buffer size. Any Task2 DTO extension belongs in the next plan, not an unrelated change during Task4.

`../helengine/engine/helengine.shader/shaders/compilation/ShaderCompileService.cs` looks up its cache before calling the backend. `ShaderCompileRequestIdentity.CreateCacheKey` includes source text hash, program/entry/stage/target/model/variant/defines/binding policy, but not resolved include contents, compiler identity, or debug/optimization/warnings-as-errors options. A backend-local cache fix cannot invalidate an already returned shared-cache hit. Next plan must test the complete service path and either extend identity or provide an explicit backend opt-out from shared caching. Do not register PS3 and silently rely on the existing key.

## Material dependencies and source selection

Backend registration must also reconcile `ShaderCompileOptions.BindingPolicy` with reflected authored binding indices. The current frontend reflects source registers and should not be assumed to apply the shared binding-policy shifts. Next plan must either implement/test the policy mapping or reject unsupported nondefault policies explicitly; never return a ProgramDefinition with shifted slots disconnected from cooked metadata.

`PlatformMaterialCookRequest` has schema fields but no separate shader asset/program/entry-point properties. The PS3 material cooker currently returns no shader dependencies. The Wii U cooker explicitly emits `PlatformShaderDependency(ForwardStandardShader, ForwardStandardShader.vs, ForwardStandardShader.ps, ForwardStandard)` and consumes editor-resolved source in WiiUShaderArtifactCooker. This is a reference seam, not permission to hardcode all PS3 programs to a standard template.

Confirmed exact source DTO: `PlatformShaderArtifactCookSource` contains only ShaderAssetId, SourceHash and SourceText. It carries neither a source path/include graph nor entry-point/variant definitions. `PlatformShaderDependency` carries asset id, logical vertex/pixel program names and variant, not entry-point function names. WiiUShaderArtifactCooker explicitly passes VS and PS (or ShadowDepthPS) and constructs platform/variant defines. A generic PS3 cooker cannot derive arbitrary entry points safely from these fields. Shared ShaderProgramDefinition has EntryPoint and Variants but is not included in this cook request. A next-plan contract extension into helengine.baseplatform/editor would require explicit scope approval beyond the already approved shared shader-library changes; alternatively an explicit injected catalog must be supplied by a supported existing caller, not a hidden PS3-only hardcoded catalog.

Refinement after exact source reads: `helengine.editor/shaders/ShaderPackageBuilder.cs` deliberately defines the engine's ordinary package convention as VS/PS with variant `default`; `StandardShaderVariants.All` is the shared explicit catalog for ForwardStandard (VS/PS), ForwardStandardShadowed (VS/PS plus HELENGINE_STANDARD_SHADOWED=1) and ShadowDepth (VS/ShadowDepthPS plus HELENGINE_STANDARD_SHADOW_DEPTH=1). Reusing that documented convention for the same supported subset is different from guessing arbitrary entry points. The next plan can choose convention-based support with explicit rejection of other selections, or propose an explicit metadata extension for arbitrary entry points. Do not introduce a second divergent StandardShader variant table.

Source path is already present on `EditorProjectShaderSource`, but is discarded at `EditorPlatformAssetCookService.CookPlatformShaderArtifacts` when constructing PlatformShaderArtifactCookSource. That precise handoff is the minimal source-path extension point if editor/baseplatform scope is approved. Relative includes must use a real source path and shared resolver, not asset-id-derived fictitious filenames.

Next plan must specify how a material selects its authored shader/program/variant and where actual entry points come from. Never infer arbitrary shader entry points from file extensions. The existing PlatformShaderArtifactCookRequest carries source text plus dependency identities, not a full entry-point manifest.

## Runtime prerequisites

Exact existing renderer boundary: Ps3RenderManager3D.cpp::ToRowMajor transposes engine float4x4 for the current embedded Cg program; Ps3RasterRenderer.cpp uploads it via rsxSetVertexProgramParameter. Authored HLSL lowering already has its own physical matrix-layout metadata. The later runtime plan must test the complete engine-matrix -> cooked layout -> RSX upload path with asymmetric translation/rotation/nonuniform scale, and must not blindly apply both the old diagnostic transpose and a second metadata-based transpose. The existing ReflectAttributes also recognizes fixed position/normal/color slots, so loading arbitrary cooked programs must consume the new attribute map instead of retaining those fixed indices. Leave the existing embedded diagnostic path untouched until that runtime task owns the changes.

PS3 `Ps3MaterialCooker` explicitly rejects textures because texture staging/runtime loading do not yet exist. `Ps3RuntimeMaterial` currently stores only base color/lit state. `Ps3RenderManager3D` calls an embedded-program renderer. Therefore texture compilation tests do not establish textured material rendering, and backend registration alone does not connect materials to shaders.

Runtime acceptance needs real program selection, resource lifetime, constant layout/endian conversion, attribute mapping and a texture fixture. Preserve existing camera clear/depth behavior and 16/32-bit mesh support. Keep `shaders` in ForcedDisabledFeatures until the actual generated-Core path builds and runs with the new runtime implementation.
